# 工程、注释与文档治理规范

- 状态：目标治理基线；实现前评审并纳入团队工程流水线
- 关联：[系统架构](02-system-architecture.md)、[需求/设计/测试追踪](04-requirement-design-test-traceability.md)、[ADR 规范](adr/README.md)

## 1. 变更前置与完成定义

每项变更先确认唯一业务 owner、范围/状态、领域不变量、API/事件/数据所有权、权限、并发和失败恢复。行为变更先更新设计和测试，再实现；在当前文档启动阶段不得创建代码/脚手架。

功能只有满足以下条件才可标为完成：

1. 需求/设计/测试 ID 完整，范围矩阵和追踪矩阵没有孤项。
2. 实现符合模块边界；迁移和 API/Event 契约有兼容/版本说明。
3. 相关自动化测试通过，数据库/provider/设备 adapter 的适用矩阵有结果。
4. 权限、并发、重试、取消、故障和审计路径已覆盖或明确说明不适用。
5. 用户/运维文档、错误信息、观测指标、部署/回滚说明同步。
6. Review 发现和未决风险关闭或有负责人/到期日期；不把警告隐藏为成功。

## 2. 后端规范

- 后端基线 .NET 10、nullable、明确 DTO/领域类型、async/CancellationToken；异步调用应将取消令牌贯穿到数据/外部 IO 边界。
- 依照模块边界组织用例和 owner；在模块内部按实际职责使用 Domain/Application/Infrastructure/API Adapter。简单用例不复制空洞层。
- Controller/Endpoint 负责 HTTP 绑定/认证/错误映射，不包含库存、Route、审批或设备状态机。
- 领域逻辑用显式状态转换/方法保护不变量，避免 EF entity setter、静态全局服务或拼接字符串中的隐藏业务条件。
- API 输入输出用稳定、有文档的 DTO；校验在服务端完成；分页/排序稳定且经过授权过滤。
- 业务错误返回稳定 code、可安全展示消息和关联 ID；不暴露堆栈、SQL、Secret 或原始设备 payload。
- 业务写操作定义并发策略、幂等和事务边界；跨模块/外部副作用以 Outbox/Inbox、状态机和补偿处理，不依赖分布式 ACID 假设。
- EF/SQL/Redis/MQ/PLC SDK 细节留在其 owner 的 Infrastructure/Adapter；不要让应用规则依赖 provider 特性而无替代/测试。
- 三个目标数据库的迁移、查询、唯一约束、并发和事务都须在 SQL Server、PostgreSQL、MySQL 验收矩阵留结果。
- 配置强类型校验；机密不进入 appsettings 样例、仓库、客户端包、普通日志或 API 回显。

## 3. 前端规范（Vue 与 UniApp）

- 运维端/Simulator 使用 Vue 3 + Vite + TypeScript；PDA 使用 UniApp + Vue 3 + TypeScript。共同遵循 Frontloom Core FE + Frontloom Vue；UniApp 专有能力经明确适配边界。
- Composition API / `<script setup>`；props/emits/model 明确类型；避免 `any`、大而全组件和业务规则复制。
- API 调用集中在 client/service 层；组件不直接依赖数据库实体、WCS 内部表或协议报文。
- Pinia 只拥有跨组件 UI/session state；服务端业务事实要从 API/query 投影恢复，不以本地 store 作权威。
- 每个页面有 loading/empty/error/unauthorized/stale/offline/success 状态；危险动作说明影响并要求按权限二次确认。
- 语义结构、键盘/扫码可用性、可访问性、响应式、输入校验、错误提示和状态恢复进入组件/E2E 测试。
- PDA 离线仅只读缓存，不保存/重放写操作；离线和缓存陈旧必须可见。
- 模拟器/SCADA 的读写权限分离；仿真/生产身份、颜色/标识和路由不可混淆。

## 4. 命名、注释与可读性

### 4.1 命名与格式

- 名称体现业务语义和所有权；状态/事件用完整稳定名称，不依赖展示文案或数字 magic value。
- 缩写只用团队已约定的领域术语（WMS、WCS、PDA、Route、Leg）；公共 API 的每个缩写在模块术语表解释。
- 私有实现避免通用 `Helper/Manager/Common` 名称；共享代码必须有真实复用、稳定职责和 owner。
- 遵循格式化、分析器和本仓命名规则；提交不包含无关重排/格式变更。

### 4.2 注释覆盖目标

注释目标是**尽量覆盖全部有维护价值的代码规则和业务意图**，不是为每一条显而易见的赋值重复写中文。注释必须解释 why、前置条件、不变量、风险、设备/数据库语义和失败后果。

- 所有公共类型、公开 API/接口、DTO、事件契约和扩展点写 XML/等价 API 文档，说明用途、参数约束、返回、异常/取消/并发和副作用。
- 每个领域状态机、库存记账点、事务/锁、幂等、防重、权限边界、补偿/重试、设备映射和多 provider 差异写明其不变量与依据。
- Route、资源预约、图模型、复杂 SQL/查询、时间窗口、硬件状态转换必须有局部解释并链接设计/测试 ID。
- 测试对非显然场景说明故障注入目的、预期不变量和用例 ID；普通断言无需逐行注释。
- 不写过期注释、代码逐字翻译、TODO 无 owner/issue 的承诺或未验证的“线程安全/安全/最优”结论。
- Review 检查注释是否与实际代码/设计同步；涉及算法的注释同步更新 Route 文档。

## 5. 文档规范

每个功能文档至少包含：

1. 状态、范围/需求 ID、owner、基线证据和关联文档。
2. 用户/系统角色、前置条件、主流程与状态机。
3. 数据 owner、不变量、并发/事务和 API/event/device contract。
4. 权限/租户/审计、异常/失败/重试/取消/补偿与可观测性。
5. 详细测试 case ID、输入/步骤、预期状态/副作用和 provider/adapter 范围。
6. 未决规则、现场输入、决策 owner 与关闭阶段。

文档先写清实现思路、为何采用、替代方案与团队上手路径；禁止仅粘贴类名/API 清单。所有相对链接可解析；术语、状态名和 ID 在范围矩阵、详细设计、测试、ADR 与验收中一致。

文档状态只能使用 `草拟 / 评审中 / 已批准 / 实施中 / 已验收 / 已废弃` 等规范值。事实错误的更正需标注证据，不得无记录地覆盖已批准行为决策。

## 6. 测试、质量门禁和 PR

- 测试从纯逻辑开始，再覆盖数据库并发/事务、API/auth、跨模块流程、协议 contract、E2E 和故障恢复。
- EF InMemory/Mock 只能验证对应抽象逻辑；不作为真实 provider 隔离级别/约束/迁移兼容证据。
- 测试必须断言持久化状态、副作用次数、owner/资源、账本流水和错误语义；只断言 HTTP 200 或对象非空不合格。
- 随机/属性测试保存种子和缩小后的反例；基准可复现并记录硬件/数据量/map version。
- PR 检查：范围与 ADR、模块依赖、权限/数据边界、migration/provider、错误处理、日志脱敏、状态/并发、用例覆盖、文档链接、注释准确性、部署/恢复。
- 任何未跑测试写明原因；失败不通过修改测试来掩盖未满足需求。安全/物理控制变更需对应负责人复审。

## 7. 版本与变更治理

API/Event/Form schema/MapVersion 的兼容策略必须明确版本和停用期限。模块边界、事务权威、设备控制、PDA 离线、provider 支持或 Route 安全假设发生变化时，必须先提 ADR，随后同步设计和测试追踪。

接口移除、表迁移、地图升级、路由行为变更和数据回填提供前向/回滚或不可逆声明；不可逆操作要审批、备份/恢复演练、审计和现场通知。
