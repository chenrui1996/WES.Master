## 2. 首批四项高风险规则签核

### 2.1 REV-01 / RULE-13：跨版本物理资源不隔离

1. Pack内物理冲突身份`physicalConflictId`稳定，MapVersion只限定图解释。任意仍活跃图版本的边/资源都映射到物理冲突集合；一次grant按这些集合检查全部活跃预约及物理占用，而不是仅查询当前图。
2. 改名保留同一物理身份；拆分/合并必须显式覆盖相交空间并验证冲突关系。容量/方向/几何/设备绑定变化默认视为不兼容，不能以不同资源ID分别grant。
3. 首期默认变更策略为`DrainAffected`：停止受影响范围接收新任务，禁止新版本运行授权；既有任务可在旧artifact及当前epoch/联锁/全量物理冲突核验下取得仅为排空所需的后续grant，不能借排空加入新任务。不可抢占段保持保护至安全点/完成；未开始任务可经owner确认无实物效果后取消，暂停在安全点本身不等于任务排空。所有既有任务已完成/安全终结、无Unknown占用后才启新版本控制。不强停安全PLC、不强撤已占资源。
4. 只有同一物理映射、能力、容量及执行语义均有兼容证据时才可显式采用`CompatibleContinue`，允许旧任务与新图任务共同受一个物理冲突域约束。没有映射或兼容证据，激活/控制门禁阻断，不能暂借两个ledger容量隔离。
5. ADR-0001的耐久权威、单writer/epoch、原子grant不变。跨Pack仍各有ledger；交接共享设备必须有唯一物理控制owner及双方握手，不假定本规则提供跨Pack原子grant。

### 2.2 REV-02 / RULE-07：审核全行原子，实物完成按执行单元

1. TransferOrder审核在同一WMS事务校验并预留全部行，任一失败整体不Approved，无有效部分预留。
2. 设备或分次人工执行后，每个已确认行/执行单元独立在WMS事务中提交来源消耗、目标收入、预留消费、行进度和Outbox。已经提交的A行不因B行失败回滚。
3. 父单主状态默认`Draft → Approved → Executing → Completed`；部分完成保留`Executing`及行级完成量。异常用独立`executionStatus=Normal/Blocked/Unknown`、`postingStatus=Pending/Synced/Failed`展示，不把一个错误覆盖所有已完成行事实。全部计划完成且记账同步后才Completed。
4. 实物已到而WMS事务失败：保存可恢复的完成事实/Inbox处理进度，来源相关预留与目标冲突保护不释放；页面显示“实物已确认，记账待同步”，不可再次分配/运输。恢复只补该执行单元一次。
5. 纯人工一次确认、尚无独立实物完成事实且所有行都在同一WMS事务的路径，才使用整单DB原子提交；若实际已分次搬运，必须走逐单元路径。物理反向属于新建受权运输，不是DB rollback。
6. 取消只终结确认未执行部分；已移动、已拣、在途及Unknown继续对账。全部未执行且安全取消才Cancelled；部分已执行后取消剩余，父单记`ClosedPartial`并保存完成/关闭余量及原因，不伪造Completed或全单Cancelled。

### 2.3 REV-03 / RULE-08：在途、交接和库存事实

1. 首期在最终目的到达且有效完成契约确认后做WMS移动；中间交接不新增库存流水。途中账面归属仍在来源维度，但对应容器/数量标为在途不可用；账面来源不表示实物仍在来源。
2. 页面分开`bookLocation`（WMS）、`executionCustodian`（执行保管权）、`observedLocation/observedAt/quality`（权威反馈）、`inTransit`与预留。定位Unknown不回退为空闲，WMS之外没有第二账本。
3. 唯一handover记录绑定transfer/容器/双方Pack/有向口/Leg/版本。目的端先给`ReadyToReceive`能力/口可接收证据，这不是激活下一Leg；源端完成交接且目的接受同一交接后，Orchestration原子推进唯一执行保管权和下一Leg激活。
4. 卸下后目的接受回执丢失：标交接待核/保管权Unknown，仍有唯一未决handover token并保护相关资源；不能让两Pack都声称可独立派发，不能让源端因未收到回执自动重新卸货。目的接收区由唯一物理owner保护，超时先query。
5. 同一容器/争议在途数量不能再次预留/派发；必要恢复必须查双方及WMS。在途与预留重合时按受保护数量并集算不可用量，同一执行单元不重复扣减：Qty10/Reserved7、其中inTransit5时Available仍3，不误算-2；Unknown继续保护该范围。不增加冻结/解冻业务。若未来要求中间交接位记账，须新需求/政策及WMS模型，不在此次偷偷增加。

### 2.4 REV-04 / RULE-20：新任务active，旧任务受控继续

1. 新任务创建/接受必须固定当前活动DeploymentId/MapVersion；禁止客户端任意指定旧部署创建新任务。
2. 旧任务命令使用其固定的taskDeploymentId/MapVersion，不因active改变而自动迁图；仅在`CompatibleContinue`或`DrainAffected`允许的排空阶段继续。每次仍核当前writer epoch、有效grant、状态新鲜度、联锁、任务/command版本及该部署已验证artifact。
3. 不兼容变更默认先排空，再切active；无法排空或Unknown未核实则不激活。受影响范围外的旧任务只有经兼容范围证明才可保留；默认按整个Pack视为受影响，不能靠前端过滤缩范围。
4. activate携`expectedActiveDeploymentId/expectedGeneration`，在Simulator本地事务CAS切指针、增加generation并写Outbox。两部署都以D1为前提时最多一个成功，另一个冲突，须重新preview/prepare/审批，不能自动覆盖。
5. Prepared绑定deployment/owner/artifact版本/hash/期望active代数及时间；初始有效期见PAR-08。重复事件幂等、漏收查manifest；回滚新建补偿部署，同样经过排空/兼容和CAS，不删除旧记录。生产激活默认被任何warning阻断，只有预先分类为非安全展示类且复核者逐条附理由的warning可放行；仿真允许受权确认warning但不把许可带入生产。
