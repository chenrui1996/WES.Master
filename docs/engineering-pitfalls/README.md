## 维护方式：开发、测试中随发现随记录

1. **开始前**：先读本索引，再按工作包涉及的技术/业务搜索相关条目，选择适用检查；不用每次加载全部历史记录。
2. **发现时**：确认可复用的坑后，在当前工作包内立即新增或更新条目，不等整包结束。先记现象、环境、证据和风险；根因未确认必须标“待定位”，不能写成确定结论。
3. **修复时**：补充根因、最小修复、禁止的绕过、回归用例与实际结果。相同问题更新原 ID，不按每次失败复制条目；历史失败不得抹去。
4. **收口前**：在工作包证据中列出本次新增/更新的条目 ID，或明确“已检查，无新增通用问题”；未解决项链接到[TodoList](../implementation/TodoList.md)或原工作包阻断，不能只在知识库里悬挂。
5. **默认值变更**：先更新批准规则/详细设计与测试，再更新这里的引用。知识库只能解释现行规则，不能自行批准新默认值、放宽权限或安全边界。
6. **验证失效**：Provider/SDK/框架升级后重新跑相关复现；未重测不得把历史规避删除或宣称不再适用。解决记录保留并注明适用版本。

此机制通过仓库治理和根目录 Agent 规则落实，不是后台自动扫描或自动汇总服务；只有实际执行开发/测试时才会更新。不要为此新增生成器、无证据定时报告或重复日志仓库。

## 条目约定

- ID 固定：`DEF-xxx` 默认值/边界，`INF-xxx` 底层/基础设施，`GEN-xxx` 通用开发测试；新条目递增，不复用旧 ID。
- 证据标签：**已复现**（已有失败/修复记录）、**基线约束**（规范要求，非已发生缺陷）、**待定位**（尚无确定根因）。
- “已修复”只对引用的工作包/版本成立；“基线约束”不得写成历史缺陷已修复。
- 每条至少含适用范围、现象/风险、原因/规则、处理/禁用绕过、验证和证据。优先链接持久化仓库文档与测试，不把会话临时路径作为唯一证据。
- 不记录连接密码、令牌、生产原始数据或完整敏感 payload；TRX/日志/临时 SQL 仍放验证目录，不复制进这里。

新增条目使用以下结构，填完再收口，不保留空模板条目：

```markdown
## GEN-xxx 标题

- 记录/更新：YYYY-MM-DD；证据标签：待定位 / 已复现 / 基线约束。
- 适用范围：模块、Provider/SDK版本、入口或状态。
- 现象与影响：输入/并发/故障条件及实际后果。
- 根因或规则：已确认事实；未知部分明确列出。
- 处理与禁用绕过：采用的修复或检查，不得采用的捷径。
- 验证：测试名/Case ID、边界输入、实际结果或尚未运行原因。
- 证据与后续：相对链接；未解决项的责任工作包/TodoList条目。
```
