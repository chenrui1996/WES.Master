## 1. 消息、Outbox 与消费者

### 1.1 契约和发布

- 命令表示“请求执行”，事件表示“已发生事实”；分别定义拥有者、版本和失败语义。
- 消息 envelope 包含 MessageId、ContractName/Version、OccurredAt、CorrelationId、CausationId、TenantId（如适用）和业务引用。
- 业务状态和必须发布的事件在同一模块事务写入 Outbox。Publisher 在租约/竞争控制下发送，发布成功后标记完成；进程退出可恢复。
- RabbitMQ/MassTransit 为可替换基础设施接入，不改变应用层事件语义；Disabled/None 是明确不可用模式，不得用于生产关键事务并伪装成功。
- 消费者至少一次接收是常态。通过 Inbox/业务幂等状态保证重复消息无重复业务效果；不可承诺无条件 exactly-once。

### 1.2 重试与死信

- 瞬时错误采用有界退避重试；永久校验/授权错误直接进入失败状态。
- 达到重试上限后死信/隔离，记录消息 ID、错误类别、尝试次数、下一步建议；运维重放需授权、幂等保护和审计。
- 不重试不可逆物理命令，除非设备契约支持命令 ID 去重、状态查询和安全的重复执行。
- 外部 Broker 不可用不丢 Outbox；容量、积压和最老消息年龄需有监控/告警。

## 2. Quartz 与后台任务

- Job 定义标注 owner、触发计划、幂等键、允许并发策略、超时、取消行为、重试和补偿。
- 多实例部署使用持久化调度/分布式互斥或业务级租约；进程内锁不能保证集群单执行。
- 定时任务执行历史可查，记录开始/结束、结果、失败类别、关联 ID、触发来源和重试次数，不记录秘密。
- Job 使用明确服务主体与租户上下文；全租户任务分批限速执行，并按租户保存进度与错误。
- 发布新 Job 版本或修改 schedule 时定义迁移/重复触发规则；启动时不能无审查地执行过期积压任务。

## 3. 告警生命周期和实时通知

### 3.1 领域状态

建议将**告警事实**与**通知投递状态**分开。事实字段包括稳定 Code、来源设备/模块、资源引用、等级、参数快照、首次/最近发生时间、重复计数、状态和关联事件。通知 delivery 按渠道保存 Pending/Sent/Failed/Retrying。

目标状态可包括 `Active → Acknowledged → Cleared`，并支持仅发生一次的事件告警；确认人、确认时间和清除来源需留痕。重复告警按 code + 资源 + 可配置窗口聚合时，必须保留计数与最近发生时间，不得静默丢事件。

Seven 现有材料确认数据库持久化和 SignalR 推送路径；是否已实现确认/清除、聚合和完整新闻管理闭环需单独核验。WES 的目标语义不得写成 Seven 已具备的行为。

### 3.2 投递渠道

- SignalR 是在线提示，不是持久化保证；客户端断线后通过受权查询恢复未读/活跃状态。
- Email/外部通知失败与告警事实解耦，按渠道重试和限流；邮件地址/模板/外部返回值不得泄露。
- 通知偏好与角色权限共同决定投递；静默/屏蔽仅影响通知，不改变告警事实或设备联锁。
- 公告/新闻有状态、发布者、受众、起止时间、撤回和已读策略；是否要求 PDA 展示由业务范围/角色确认，不能将公告当紧急告警通道。

## 4. 缓存与 HotStore 边界

- 普通缓存采用可失效的读优化；定义 key、TTL、失效事件和缓存穿透/雪崩策略。
- HotStore 只存明确定义的高频运行时快照/状态，不作为库存账本、唯一任务记录或不可恢复的预约事实。
- 调度安全相关预约若需重启后保持有效，必须有 durable owner/lease/恢复校验；不能只凭 Redis key 尚在就认为车辆仍占有资源。
- 缓存 unavailable 时，对可降级查询可回源并限流；安全/一致性依赖丢失时应暂停相关动作并显式报错。
- 禁用时返回清晰的 Disabled/NotSupported 语义，禁止空成功对象伪装可写热状态。

## 5. 可观测性与运维

- 指标：Outbox 数量/年龄/失败、消费者延迟/重试/死信、Job 成功率/持续时间、告警活跃/重复数、通知投递失败、HotStore 健康状态。
- 日志用 correlation/message/job/alert ID 关联跨模块流程；业务内容做最小化和脱敏。
- 运维重放/清理/解锁需权限、理由、目标 ID、前后状态和审计事件。
- 对可能驱动物理设备的消费者提供暂停/熔断入口；暂停期间持久化排队，并确保超时任务不自动下发过期控制命令。

## 6. 详细验收用例

| ID | 场景 | 期望 |
|---|---|---|
| NTF-TC-001 | 业务提交和 Outbox 同事务，数据库故障/事务回滚 | 两者共同成功或共同失败，无幽灵事件 |
| NTF-TC-002 | Broker 不可用后恢复，Publisher 中途崩溃 | Outbox 最终可发布，重发不造成第二次业务效果 |
| NTF-TC-003 | 消费消息重复、乱序、消费者执行后 ACK 前崩溃 | 幂等处理/版本校验保证一次逻辑效果，可观察重试 |
| NTF-TC-004 | 永久错误、瞬时错误、超过重试上限 | 分别拒绝、退避重试、进入死信并保留诊断信息 |
| NTF-TC-005 | 未授权重放/重复重放/错误消息版本重放 | 拒绝或安全去重；每次管理动作留审计 |
| NTF-TC-006 | 两个 Quartz 节点同时触发同一任务 | 满足定义的集群互斥或幂等规则，不发生双重副作用 |
| NTF-TC-007 | Job 超时、取消、重启恢复与旧计划升级 | 进度状态可判定，不重复执行不可逆动作 |
| NTF-TC-008 | 租户 Job 缺少上下文或运行中租户隔离 | fail closed；不得处理其他租户数据 |
| NTF-TC-009 | 告警新建、重复、确认、清除及并发变化 | 状态转换确定；重复计数、操作者、时间完整保留 |
| NTF-TC-010 | SignalR 断线、重连、重复推送和权限变化 | 查询能恢复权威状态；不将推送送至未授权主体 |
| NTF-TC-011 | 邮件渠道永久/临时失败 | 告警事实保持；delivery 单独重试/失败且可查询 |
| NTF-TC-012 | 公告过期、撤回、跨受众和租户访问 | 受众范围正确；过期/撤回内容不被新会话继续显示 |
| NTF-TC-013 | Redis/HotStore 故障、陈旧快照和重启 | 不把过期/不存在状态当作有效预约或业务成功 |
| NTF-TC-014 | HotStore 禁用后调用写 API | 返回明确未启用结果；不静默丢写或返回成功形状 |
| NTF-TC-015 | 高积压、消息延迟和指标标签检查 | 告警可触发，指标无用户/单号/设备等无限基数标签 |
