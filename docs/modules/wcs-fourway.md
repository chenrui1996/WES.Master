# FourWay WCS 详细设计

- 状态：目标设计；保留 Seven 业务骨架，路线/交通/预约模型须通过 Route 专项重构
- 范围追踪：`SCOPE-WCS-02`
- 基线参考：[WMS/WCS 实现说明](../../../Seven.Master/doc/20-WMS与WCS实现说明.md)、[Route 现状分析](../route/01-as-is-and-research-review.md)、[Route 目标设计](../route/02-target-routing-and-scheduling.md)
- 测试前缀：`FW-TC-*`

## 1. 包边界与状态实体

FourWay 拥有层/巷/位策略、Shuttle 任务和路径点列、层内 map version/graph、交通资源与边占用、停车位状态、提升机设备/口/执行任务和本包反馈。WMS 拥有库存和库位主数据；Orchestration 拥有跨包订单/Leg；Device Adapter 拥有协议会话。

FourWay 不写库存数量；每个运行状态和预约必须有 owner、生命周期、租约/恢复语义以及关联的 Leg/Task/Vehicle/MapVersion。

## 2. 目的地分配

分配流程：按仓/Pack 过滤可用层策略 → 选择层 → 选择该层可用巷道（空位阈值按层统计、车数上限约束）→ 选择巷内可用目标位 → 原子预约目标位置。优先级、分配权重、轮转和同分 tie-break 必须稳定，记录策略版本与选择依据。

`CanHandle` 检查 FourWay 货位或已知交接点；纯 Stacker 位置不能因默认候选被误接。不同层 Leg 进入提升机流程，不能误用同层路由图。

## 3. 层内路径与交通预约

当前 Router 是基于非负权重的图最短路；PathDispatcher 解析 map version，保存路径点列，TrafficGuard 对下一边尝试预约，反馈后释放已通过资源并申请下一段。无地图/无边的兼容单段行为必须由显式配置和场地风险评审决定，不可静默当作可证明安全的路径。

目标设计将区分：

1. 静态图合法性与可达性（节点、边、方向、冲突区、地图版本）。
2. 单车候选路线成本（距离/代价/设备能力，确定 tie-break）。
3. 多车时间窗资源约束（边、节点、交叉区、提升机/狭窄区和停车位）。
4. 运行时车辆位置、方向、载荷、遥测新鲜度和命令/反馈状态。
5. 预约原子 grant/release、租约和崩溃恢复，以及等待环/饥饿处置。

Route reservation authority 遵循 [ADR-0001](../adr/ADR-0001-route-reservation-authority.md)。算法详细不变量、理论边界和仿真测试在 Route 专项中统一定义；本模块不得另建不同的权重或死锁判定语义。

## 4. 停车预约和出库

出库 Retrieval 按 WcsGroupNo/WcsPri 门闩推进；Shuttle 获取可用停车资源后尝试路线预约。只有车辆实际启动/状态符合条件后才将停车资源从 Reserved 转到 Occupied；无空闲位任务进入 Suspended 并在资源释放时公平唤醒。完成/取消/失败释放与该车/任务相匹配的资源，不能释放其他车预约。

状态必须区分 `Free → Reserved(owner, lease) → Occupied(owner) → Free`；Reservation 与真实车辆位置不一致时转入异常核验，不允许后台扫表直接释放活车占用。取消/失败仅可直接释放尚未进入物理占用的 reservation；已占用资源须在权威反馈确认车辆离开后释放，未知位置持续保护。

## 5. 跨层提升机流程

保持一个 Orchestration Leg，在 FourWay 内部执行三个受控阶段：

1. `ToSrcAp`：源货位至源层提升机 AP。
2. `HoistLift`：提升机按同口队列和安全互斥规则跨层到目标 EP。
3. `FromDesEp`：目标层 EP 至目标货位。

同提升口同一时刻仅允许一个符合设备约束的执行任务；后续任务显式 Suspended/Queued，并在前任务完成/失败后调度。每阶段命令、AP/EP、车辆/容器、反馈和重试关联到同一个 Leg/HoistTask。失败不会自动跳过阶段；若货物可能已在提升机或口内，标记位置未知并要求状态查询/人工处置。每次阶段切换使用幂等状态版本，重复/乱序反馈不能前进多阶段。

## 6. 异常和恢复

- Route 失败/冲突等待：保持安全等待并更新等待原因；不下发未预约的冲突边。
- 停车位耗尽：进入有界、公平等待并监测等待时间；资源恢复按策略唤醒。
- 遥测陈旧/车辆当前位置未知：停止新预约/推进，保留资源保护，启动定位恢复流程。
- 反馈 `NotOk`、丢失、重复或 out-of-order：只在合法状态转移时更新；未知状态不得估算成功。
- 任务取消/失败：释放尚未占用资源；已占用资源需先确认车辆离开/释放，再回收。
- HotStore 恢复：重建/校验持久任务与预约 owner；不以缓存键是否存在作为物理事实。
- 从统一 2D 运维地图发起的强制完成/重发/模式切换仍需单独授权、现场状态确认、审计与安全互锁；FourWay Pack 做最终检查，安全 PLC 为最终物理保护。
- Pack 必须在命令执行前重新校验车辆遥测新鲜度、任务版本、预约 owner、提升机阶段和联锁；跨包协调与操作者工作流见 [Orchestration 运维协调](orchestration.md#8-wcs-运维协调边界)，本包保留最终执行/拒绝权。

## 7. 详细验收用例

| ID | 场景 | 期望 |
|---|---|---|
| FW-TC-001 | 多层/巷策略启停、权重和轮转 | 只选合法层巷，选择依据确定 |
| FW-TC-002 | `MinEmptySlots` 按层边界、`MaxShuttleCount` 满额 | 边界值准确，满额巷不再接单 |
| FW-TC-003 | 同层有效位置、禁用位、不同 Pack 位置和错误前缀 | 仅目标包可用位置能预约 |
| FW-TC-004 | 并发入库分配争用同一目标位 | 单个原子预约成功，其他请求选择替代或明确失败 |
| FW-TC-005 | 地图版本显式 ID/LayerCode/Active/无匹配 | 解析规则显式、确定；不使用任意首记录 |
| FW-TC-006 | 有权重路径、相同代价、无路、负/非法权重 | 路由符合定义；非法图拒绝；无路不伪造成功 |
| FW-TC-007 | 多车相向、交叉、共享边时间重叠 | 冲突资源不会同时授予；等待/重规划可追踪 |
| FW-TC-008 | 预约后取消、失败、断线和进程重启 | 只释放匹配 owner 的未占用资源；活车占用不被误清 |
| FW-TC-009 | 停车位 Free→Reserved→Occupied→Free | 并发不双重预约；状态变化符合车辆实际反馈 |
| FW-TC-010 | 停车位耗尽及回收唤醒 | 任务等待；释放后按公平规则唤醒而不饥饿 |
| FW-TC-011 | 同组高/低优先级、多组任务 | 排序符合策略且有 aging/fairness 上界 |
| FW-TC-012 | 跨层三个阶段逐个反馈 | AP→提升→EP→目标位顺序完整，最终只完成一个 Leg |
| FW-TC-013 | 同提升口并发任务、前任务失败/超时 | 后续排队；未知物理位置时不安全推进 |
| FW-TC-014 | 同一提升阶段反馈重复/乱序/错误容器 | 不多推进、不串任务；可观测拒绝原因 |
| FW-TC-015 | 遥测过期、车辆重启改 ID、map version 更新 | 暂停新冲突动作并要求恢复/版本策略，不用陈旧坐标规划 |
| FW-TC-016 | HotStore/Redis 失效并恢复 | 状态可由耐久 owner 恢复并校验；不重复派车 |
| FW-TC-017 | 从 2D 运维地图强制完成/重发/控制模式越权 | 服务端拒绝或要求强审计；普通用户无物理命令，地图只展示 Pack 回读的真实状态 |
| FW-TC-018 | 大图、多车、多任务仿真基准 | 固定地图/车辆/任务/硬件环境记录，按 Route 专项定义的阈值报告 |
